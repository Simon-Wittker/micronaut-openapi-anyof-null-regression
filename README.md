# Micronaut OpenAPI generator: enums/models generated incorrectly with Micronaut 5.2.4

Minimal reproducer showing a regression in the Java code generation from an OpenAPI spec
(`micronaut-openapi` Gradle plugin) between **Micronaut 4.10.18** and **Micronaut 5.2.4**.

## Summary

Properties that are declared in the spec as

```json
"category": {
  "anyOf": [
    { "$ref": "#/components/schemas/SearchCategory" },
    { "type": "null" }
  ]
}
```

(`SearchCategory` is a plain string enum) are generated correctly in 4.10.18, but in 5.2.4 the generator
creates **wrapper classes instead of the referenced enum** (e.g. `SearchResultCategory`,
`EntityReferenceRelationType`, `LegalFormCode`, `LicenseTypeCode`, `InsuranceLineCode` are no enums anymore) and, for
`$ref`s to models, wrong/duplicated types (e.g. `InsuranceBrokerageLegalForm` instead of `LegalForm`).

| Property                          | Micronaut 4.10.18 (OK)  | Micronaut 5.2.4 (broken)                          |
|-----------------------------------|-------------------------|---------------------------------------------------|
| `SearchResult.category`           | `SearchCategory` (enum) | `SearchResultCategory` (empty class, no values)   |
| `EntityReference.relationType`    | `RelationType` (enum)   | `EntityReferenceRelationType` (empty class)       |
| `SearchResult.legalForm`          | `LegalForm`             | `InsuranceBrokerageLegalForm` (wrong, duplicate)  |
| `SearchResult.licenseType`        | `LicenseType`           | `InsuranceBrokerageLicenseType` (wrong, duplicate)|
| `InsuranceBrokerage.legalForm`    | `LegalForm`             | `InsuranceBrokerageLegalForm` (wrong, duplicate)  |
| `InsuranceLine.code`              | `InsuranceLineCode` (enum) | `InsuranceLineCode` (model class, not an enum) |
| `LegalForm.code`                  | `LegalFormCode` (enum)  | `LegalFormCode` (model class, not an enum)        |
| `LicenseType.code`                | `LicenseTypeCode` (enum)| `LicenseTypeCode` (model class, not an enum)      |
| `InsuranceBrokerage.address`      | `Address`               | `InsuranceBrokerageAddress` (duplicate)           |
| `InsuranceLine.label` etc.        | `MultiLanguageLabel`    | `InsuranceLineLabel`, `LegalFormLabel`, ... (duplicates) |
| query param `lang` / `category`   | `Language` / `SearchCategory` | `...LangParameter` / `...CategoryParameter` wrapper classes |

The spec is OpenAPI 3.1 (generated by FastAPI/Pydantic), which uses `anyOf` with `null` for optional fields.

## Layout

```
iir-finma-api.json    # the OpenAPI spec (shared by both projects)
Justfile              # `just test-compare` / `just clean-test-compare`: runs the tests of both projects
micronaut-4-10-18/    # Micronaut 4.10.18, io.micronaut.openapi plugin 4.6.2   -> works
micronaut-5-2-4/      # Micronaut 5.2.4,   io.micronaut.openapi plugin 5.0.2   -> broken
```

Both projects are reduced to the bare minimum (`io.micronaut.library` + `io.micronaut.openapi` plugin, no application code) and are identical apart from the Micronaut/plugin versions. The generator is configured in
`build.gradle.kts` of each project:

```kotlin
micronaut {
    openapi {
        client(file("../iir-finma-api.json")) {
            lang = "java"
            apiPackageName = "ch.finma.iir.client.api"
            modelPackageName = "ch.finma.iir.client.model"
            useReactive = false
        }
    }
}
```

## Environment / versions

Both projects are identical except for the versions below (resolved with `./gradlew dependencies` / `buildEnvironment`):

| Component                                    | `micronaut-4-10-18` (OK) | `micronaut-5-2-4` (broken) |
|----------------------------------------------|--------------------------|----------------------------|
| Micronaut (`micronautVersion` in `gradle.properties`) | 4.10.18         | 5.2.4                      |
| Micronaut Gradle plugins (`io.micronaut.library`, `io.micronaut.openapi`) | 4.6.2 | 5.0.2     |
| `io.micronaut.openapi:micronaut-openapi` (resolved) | 6.20.1            | 7.3.0                      |
| `org.openapitools:openapi-generator` (resolved, transitive) | 7.16.0    | 7.22.0                     |
| Gradle (wrapper, `gradle-wrapper.properties`) | 9.1.0                   | 9.6.0                      |
| JDK                                          | 25 (tested with Azul Zulu 25) | 25 (tested with Azul Zulu 25) |
| OS                                           | macOS                    | macOS                      |

Note: the generator version is not set explicitly anywhere. It is pulled in transitively by the `io.micronaut.openapi`
Gradle plugin, so the difference in behaviour can come from the Micronaut OpenAPI generator (`micronaut-openapi` 6.20.1 -> 7.3.0),
from the upstream OpenAPI Generator (7.16.0 -> 7.22.0), or from both. This has **not** been narrowed down yet.

The Gradle wrappers are included, no local Gradle installation is needed. Network access to Maven Central and
`services.gradle.org` is required for the first run.

## Reproduce

Requires JDK 25 (as in the generated projects).

Quickest way: with [`just`](https://github.com/casey/just) installed, run both projects in one go from the repository root.
It prints a PASS/FAIL summary for both Micronaut versions at the end (expected: 4.10.18 `PASS`, 5.2.4 `FAIL`):

```bash
just test-compare         # ./gradlew test in both projects
just clean-test-compare   # ./gradlew clean test in both projects (forces re-generation of the code)
```

Or run the projects manually without `just`:

```bash
# 4.10.18 -> all tests pass
cd micronaut-4-10-18
./gradlew test --tests '*GeneratedEnumsTest'

# 5.2.4 -> all 8 tests fail
cd ../micronaut-5-2-4
./gradlew test --tests '*GeneratedEnumsTest'
```

`GeneratedEnumsTest` (identical in both projects, `src/test/java/ch/finma/iir/`) checks the generated model classes
via reflection. It contains 8 tests:

| Test                                           | Checks                                                           |
|------------------------------------------------|------------------------------------------------------------------|
| `searchResultCategoryReusesSearchCategoryEnum` | `SearchResult.category` is the enum `SearchCategory`             |
| `entityReferenceRelationTypeIsEnum`            | `EntityReference.relationType` is an enum                        |
| `searchResultReusesLegalFormModel`             | `SearchResult.legalForm` is of type `LegalForm`                  |
| `searchResultReusesLicenseTypeModel`           | `SearchResult.licenseType` is of type `LicenseType`              |
| `insuranceBrokerageReusesLegalFormModel`       | `InsuranceBrokerage.legalForm` is of type `LegalForm`            |
| `insuranceLineCodeReusesInsuranceLineCodeEnum` | `InsuranceLine.code` is the enum `InsuranceLineCode`             |
| `legalFormCodeReusesLegalFormCodeEnum`         | `LegalForm.code` is the enum `LegalFormCode`                     |
| `licenseTypeCodeReusesLicenseTypeCodeEnum`     | `LicenseType.code` is the enum `LicenseTypeCode`                 |

Generated sources can be compared directly:

```bash
diff -r micronaut-4-10-18/build/generated/openapi micronaut-5-2-4/build/generated/openapi
```

Generated code is located in `build/generated/openapi/generateClientOpenApiModels/src/main/java/ch/finma/iir/client/model/`
(tasks `generateClientOpenApiApis` / `generateClientOpenApiModels`).

## Expected vs. actual

- **Expected** (4.10.18): `SearchResult` has `private SearchCategory category;`, where `SearchCategory` is an enum
  with `INTERMEDIARIES`, `BROKERAGES`.
- **Actual** (5.2.4): `SearchResult` has `private SearchResultCategory category;` and `SearchResultCategory` is an
  empty class (only `equals`/`hashCode`/`toString`), so the enum values cannot be (de)serialized.
  Likewise `LegalForm.code`, `LicenseType.code` and `InsuranceLine.code` are generated as model classes
  (`LegalFormCode`, `LicenseTypeCode`, `InsuranceLineCode`) instead of enums.

## Details for analysing the problem

### Relevant part of the spec

The spec (`iir-finma-api.json`, OpenAPI **3.1.0**, produced by FastAPI/Pydantic) contains no inline enums for the affected
properties. Every affected property is an `anyOf` of a `$ref` and `null`, and the referenced schema is a top-level
string enum (or an object that contains such a property):

```json
"SearchCategory": { "type": "string", "enum": ["INTERMEDIARIES", "BROKERAGES"], "title": "SearchCategory" },
"LegalFormCode":  { "type": "string", "enum": ["NATURAL_PERSON", "AG", "GMBH", "..."], "title": "LegalFormCode" },
"LegalForm": {
  "type": "object",
  "properties": {
    "code":  { "anyOf": [ { "$ref": "#/components/schemas/LegalFormCode" }, { "type": "null" } ] },
    "label": { "anyOf": [ { "$ref": "#/components/schemas/MultiLanguageLabel" }, { "type": "null" } ] }
  }
}
```

The same pattern is used for `SearchResult.category`, `SearchResult.legalForm`, `SearchResult.licenseType`,
`InsuranceBrokerage.legalForm`, `InsuranceBrokerage.address`, `InsuranceLine.code`, `InsuranceLine.label`,
`LicenseType.code`, `EntityReference.relationType` and for the query parameters `lang` / `category`.
Search the spec for `anyOf` to see all occurrences.

### Generated code: before / after

`SearchResult` in `micronaut-4-10-18` (excerpt):

```java
import ch.finma.iir.client.model.SearchCategory;
...
private SearchCategory category;
```

`SearchResult` in `micronaut-5-2-4` (excerpt):

```java
private SearchResultCategory category;   // wrong type, SearchCategory is not used
```

and the generated `SearchResultCategory` (as well as `LegalFormCode`, `LicenseTypeCode`, `InsuranceLineCode`) is an empty
`@Serdeable` class without any enum constants, only with `equals`/`hashCode`/`toString`:

```java
@Serdeable
@Generated("io.micronaut.openapi.generator.JavaMicronautClientCodegen")
public class SearchResultCategory {
    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { return Objects.hash(); }
    @Override public String toString() { return "SearchResultCategory()"; }
}
```

The enums `SearchCategory`, `RelationType` and `Language` are still generated as real enums in 5.2.4, they are just not
referenced by the properties that use them via `anyOf` + `null`.

The generated files of both versions are in the `build/` directories after a test/generate run. The complete list of
generated model files differs as well: 5.2.4 additionally generates `SearchResultCategory`, `EntityReferenceRelationType`,
`InsuranceBrokerageLegalForm`, `InsuranceBrokerageLicenseType`, `InsuranceBrokerageAddress`, `InsuranceLineLabel`,
`LegalFormLabel`, `LicenseTypeLabel`,
`GetInsuranceIntermediaryApiV1GenericIntermediariesIdGetLangParameter` and `SearchApiV1GenericSearchGetCategoryParameter`.
In addition, `ValidationErrorLocInner` (4.10.18) is named `LocationInner` in 5.2.4 (naming difference only, unrelated to this problem).

### Where to look

- Generator class (see `@Generated` annotation in the generated sources): `io.micronaut.openapi.generator.JavaMicronautClientCodegen`
  in the `micronaut-openapi` repository (module `openapi-generator`).
- Suspected area (hypothesis, not verified): handling of `anyOf: [ {$ref}, {type: null} ]` (OpenAPI 3.1 nullable pattern),
  which seems to be treated as an inline composed schema (-> new "wrapper" model named `<Parent><Property>`) instead of
  being resolved to the referenced schema. Compare with the behaviour of the upstream OpenAPI Generator 7.16.0 vs. 7.22.0.
- Not tested yet whether the same happens with `lang = "kotlin"` or with a server (`server(...)`) instead of a client generation,
  or with an OpenAPI 3.0 style `nullable: true` spec.

## Working with the reproducer

### Re-generating the code

The generated sources are written to `build/generated/openapi/` and are cached by Gradle. To make sure the code is
really regenerated (e.g. after changing the spec, the plugin or the generator), use:

```bash
cd micronaut-5-2-4
./gradlew clean generateClientOpenApiModels generateClientOpenApiApis
# or run everything including the tests
./gradlew clean test
```

Compilation of the generated code **succeeds** in both versions, the problem only becomes visible in the generated types
(and therefore in the `GeneratedEnumsTest`, or at runtime when (de)serializing e.g. `"category": "BROKERAGES"`).

The `Justfile` targets (`just test-compare`, `just clean-test-compare`, see [Reproduce](#reproduce)) are also handy while
developing a fix, because they run both projects and show the result side by side.

The HTML test reports are written to `<project>/build/reports/tests/test/index.html`.

### Expected test result

- `micronaut-4-10-18`: `BUILD SUCCESSFUL`, 8 tests passed.
- `micronaut-5-2-4`: `BUILD FAILED`, 8 tests failed (no compile errors). The assertion messages show the actual
  generated type, e.g. `ch.finma.iir.client.model.SearchResultCategory` instead of `...SearchCategory`.

If your fix works, `micronaut-5-2-4` must behave like `micronaut-4-10-18`: all 8 tests green.

### Testing a fix with a local build of `micronaut-openapi`

The projects use released versions from Maven Central. To test a fix of the generator, build your local checkout of
[micronaut-projects/micronaut-openapi](https://github.com/micronaut-projects/micronaut-openapi) and make `micronaut-5-2-4`
use it. One possible way (adapt to your setup, not tested in this repository):

1. In the `micronaut-openapi` checkout publish the artifacts to the local Maven repository:

   ```bash
   ./gradlew publishToMavenLocal
   ```

2. In `micronaut-5-2-4/settings.gradle.kts` make the local repository available to the Gradle plugin classpath:

   ```kotlin
   pluginManagement {
       repositories {
           mavenLocal()
           gradlePluginPortal()
           mavenCentral()
       }
   }
   ```

3. Force the locally published version of the generator on the plugin classpath, e.g. in `micronaut-5-2-4/build.gradle.kts`:

   ```kotlin
   buildscript {
       repositories { mavenLocal(); mavenCentral() }
       configurations.classpath {
           resolutionStrategy.eachDependency {
               if (requested.group == "io.micronaut.openapi") {
                   useVersion("<your-local-version>")   // e.g. 7.3.1-SNAPSHOT
               }
           }
       }
   }
   ```

4. Run `./gradlew clean test` and check with `./gradlew buildEnvironment | grep micronaut-openapi` that your version
   is really used.

Alternatively, a composite build (`includeBuild("../micronaut-openapi")` in `pluginManagement`) can be used.

To check whether a bug is in the upstream OpenAPI Generator instead, run the same spec with the plain
`org.openapi.generator` Gradle plugin using the generator versions 7.16.0 and 7.22.0 (`java` / `micronaut` generator).
